# TESTING — test strategy and levels

This document describes **what** we test, **where** it runs and **what blocks a
merge**. Running these tests is described in [CI.md](CI.md); the rules for
developing the SDK itself — [SDK.md](SDK.md).

---

## 1. Principles

1. **The default place for a test is the host, not the board.** Hardware is
   slow, non-deterministic and scarce. Only what physically cannot be checked
   any other way goes onto hardware (section 5).
2. **Time to feedback is a requirement.** Firmware unit tests: seconds. A full
   PR: minutes. HIL: overnight. A test nobody waits for stops being run
   deliberately.
3. **Tests are deterministic or they do not exist.** Simulated time, not
   `sleep`. Randomness from a seeded RNG. A flaky test goes into quarantine for
   24 h and is then fixed or deleted — never "retry and move on".
4. **We do not chase a coverage percentage.** We chase the list of mandatory
   scenarios (sections 3–11). Coverage is reported as information, not as a gate.
5. **We test our code, not somebody else's.** We do not test the vendor HAL, the
   Thread stack in the NCP or the phone's operating system — we test our use of
   them and our behaviour when they fail.

---

## 2. Test map

| Level | What it covers | Where it runs | When |
|---|---|---|---|
| Contract | `pkpu-proto`, backward compatibility of frames, schemas | host | every PR |
| Firmware unit | `pkpu-device-core`, `pkpu-link`, `apps/` logic | host + mock platform | every PR |
| Portability | target matrix build, image size, `cfg` lint | host (cross-build) | every PR |
| Platform conformance | the suite every `Platform`/`Link` impl must pass | host (mock) + HIL | PR + nightly |
| Cloud unit | service logic, rules, reconcile, presence | host | every PR |
| Cloud integration | Postgres/Timescale, NATS, MinIO in containers | host (testcontainers) | every PR |
| Mobile core | provisioning machine, cache, API client | host + fake BLE/NFC | every PR |
| Virtual E2E | the full flow with the device simulator | host (compose) | main + nightly |
| HIL | flash, radio, current draw, OTA with the bootloader | the rig with boards | nightly + before a release |
| Fleet | staging tenant, canary cohort, soak | staging / production | before every rollout |

## 3. Contract tests (`pkpu-proto`)

The cheapest class of tests in the project with the highest return — one frame
decoded differently on the two sides costs more than the whole rest of the suite.

- **Round-trip**: `encode -> decode == original` for every type, property-based
  (`proptest`) over random values, not over three hand-picked ones.
- **Golden vectors**: the `proto/tests/vectors/` directory with frame bytes
  generated by **previous** versions of the contract. New code has to decode
  them. A vector file may be appended to, never modified — modifying it is a
  deliberate compatibility break and requires a `v` bump in `Envelope`.
- **Enum agreement with the database**: a test generates the variants from Rust
  and compares them with `CREATE TYPE` in the migrations ([DATA.md](DATA.md)
  section 2). `ComType::Zigbee = 2` drifting from the PG enum is meant to be a
  CI failure, not a production incident.
- **Schema snapshots**: the generated JSON Schema and OpenAPI live in the repo. A
  PR that changes them shows a diff in review — an API change is visible rather
  than discovered by a client.
- **Decoder fuzzing** (`cargo-fuzz`): the `Envelope` decoder processes
  **untrusted data from the radio**. The requirement: no input causes a panic, an
  infinite loop or an out-of-bounds read. The corpus is kept between runs and
  every crash lands in the repo as a regression test.

## 4. Firmware — tests on the host

The foundation: `pkpu-device-core` does not know the hardware
([DEVICE.md](DEVICE.md) section 3), so it compiles for the host with a set of
fakes.

| Fake | Replaces | What it gives |
|---|---|---|
| `pkpu-platform-mock` | the `Platform` impl | flash in RAM with wear and write-error simulation, deterministic RNG, a controllable clock |
| `MockLink` | the radio | an in-memory channel with configurable MTU, RTT, packet loss and disconnections |
| simulated time | `embassy-time` | hours of device operation in milliseconds of test time |

Mandatory scenarios:

- **Telemetry life cycle**: measurement → RAM buffer → overflow → flash → loss
  of connectivity → recovery → batch send with `backfill = true`. No duplicates,
  no gaps in `seq`, no writes to flash while it still fits in RAM.
- **Power loss at every OTA step**: a test parameterized by the interruption
  point (download, verification, slot write, switch-over, first boot). The
  expectation is always the same: the device boots into a **working** image.
- **Rollback**: no `mark_boot_ok()` across N boots → return to the previous slot,
  `DeviceIdentity` intact.
- **Command idempotency**: the same `command_id` delivered twice → one
  execution, two ACKs. A command past its TTL → rejected, not executed late.
- **Backoff**: 10,000 simulated devices starting simultaneously after a cloud
  outage — the distribution of retries has to be spread out in time. A
  thundering herd does not show up with a single device, so the test has to be
  statistical.
- **Provisioning**: the full sequence from [DEVICE.md](DEVICE.md) 6.1 together
  with the error paths — a bad cloud signature (creds **rejected**), a timeout,
  a device already claimed, a reset in the middle of the sequence.
- **Factory reset**: erases the creds and the assignment, keeps the identity.
- **Link degradation**: an MTU 80 B / RTT 2 s profile (Zigbee) — the core
  fragments and slows down instead of clogging the queue; a 1500 B profile
  (Wi-Fi) — it does not waste windows.

A panic in the firmware is a failure, not an exception: the suite is also run in
a mode where `panic` = a failed test, and the public SDK API does not use
`unwrap()` on the runtime path (see [SDK.md](SDK.md) section 3).

## 5. Firmware — tests on hardware (HIL)

The rig: probe-rs + `defmt` over RTT, a controllable power supply (to force
brownouts), a current analyzer (PPK2 / Otii), one board from **every** MCU
family in the matrix ([DEVICE.md](DEVICE.md) 4.2).

| Test | Why hardware only |
|---|---|
| Flash life cycle | real sector geometry, erase times, power loss mid-write |
| End-to-end OTA | a real bootloader, real signature verification, a real slot switch |
| Forced rollback | a brownout inside the boot window — it cannot be simulated credibly |
| Current draw | section 7 |
| Radio | RSSI/LQI, network join, behaviour at the edge of range, reconnection after losing the parent |
| Watchdog and reset reason | a peripheral, not logic |
| RTC drift and wake-up time | depends on the crystal, the temperature and the individual unit |

HIL tests are written as tests (`embedded-test` / `defmt-test`) run from CI, not
as a procedure for an operator — otherwise they will not survive the first month.

## 6. Portability and conformance

Two different questions, two different mechanisms.

**Does it build** — the target matrix from [DEVICE.md](DEVICE.md) 4.2 on every
PR, a lint forbidding `cfg(target_arch|target_os)` outside `pkpu-platform-*` and
`boards/`, an image size report with a regression threshold.

**Does it behave the same** — the **conformance suite**: one set of tests
parameterized by the implementation, run against the mock (PR) and against every
real platform (HIL). It is the `Platform` contract expressed executably:

```
conformance::flash     write/read/erase, sector boundaries, state after a reset
conformance::clock     monotonicity, wake-up within tolerance, wall-clock after sync
conformance::rng       no repeats, statistical tests over a sample
conformance::identity  reading device_id, a signature verifiable with the public key
conformance::ota       slot write, mark_boot_ok, rollback, rejection of a foreign `platform`
conformance::reset     the reset reason recognized for every source
conformance::power     entering/leaving low-power mode, RAM retention
conformance::link      connect/send/recv, the declared LinkProfile matching the measurement
```

A port to a new platform is **finished when it passes conformance on
hardware** — not when it compiles. That is the only definition that does not
drift from reality, and it is what turns portability from a declaration into a
property.

## 7. Energy tests as regression tests

The budget from `product.toml` ([DEVICE.md](DEVICE.md) section 11) is an
assertion, not a comment:

```
scenario:  measurement cycle × N, repeated, with a real radio
measured:  charge [uC] per cycle, sleep current, radio window duration
assertion: average current <= avg_current_ua from product.toml + a 10% margin
report:    trend per commit; a rise > 5% requires justification in the PR
```

Without this an energy regression surfaces in the field a year later, as
"the batteries die faster than we promised" — that is, at the point where it
cannot be fixed with an update. The budget is not portable across platforms
(ADR-011), so the threshold is defined per `platform` + `board`.

## 8. Cloud

- **Unit**: rule evaluation, shadow reconcile, the presence watchdog (with
  injected, not system, time), cohorting and OTA gates.
- **Integration** (`testcontainers`): a real Postgres+Timescale, NATS, MinIO.
  `sqlx` verifies the queries at compile time, but hypertables, continuous
  aggregates and retention policies have to be checked against a live database.
- **Tenant isolation** — a separate, mandatory class of tests: for every
  endpoint and every table, an access attempt with another tenant's token must
  return nothing or a 403. RLS is the safety net, the test is the proof that it
  is taut.
- **Migrations**: `up` against a copy of the production schema plus a backward
  compatibility test — the previous binary version has to work against the new
  schema, because the deployment is a rolling one ([CI.md](CI.md) section 6).
- **Load**: `pkpu-ingest` with a virtual fleet (section 9) at the target and the
  peak profile. The peak profile is the whole fleet reconnecting at once after a
  network outage — a real scenario, not a theoretical one.
- **Chaos**: killing NATS, the database and MinIO while traffic is flowing. The
  requirement: no silent data loss — either an ACK, or the device retransmits.
- **Recovery**: restoring the database from JetStream within the SLO window
  (< 30 min, [CLOUD.md](CLOUD.md) 10) — tested, not assumed.

## 9. The device simulator and the virtual fleet

`pkpu-simulator` — a host binary running the **real** `pkpu-device-core` on
`pkpu-platform-mock`, with `Link` wired to a real MQTT. It is not a protocol
stub: it is the very same code that ships on the device.

Uses:
- E2E without hardware: provisioning → telemetry → command → OTA → rollback,
- scale tests: N thousand instances with `SLEEP` and `NONSLEEP` profiles,
- incident replay: the simulator fed with traffic recorded in the field,
- cloud development without a single board in the loop.

What the simulator does **not** take off the table: time, current and flash. A
green simulator with a red HIL means a bug in the platform layer, not in the
logic — and conversely, a green HIL with a red simulator means the HIL test is
too shallow.

---

## 10. Mobile

- `pkpu-core` on the host with a fake `BleTransport`/`NfcTransport` — the whole
  provisioning machine, including the error paths from [MOBILE.md](MOBILE.md)
  section 3.
- A smoke test of the UniFFI bindings on both platforms: does the artifact load
  and do the types cross the FFI boundary. That is the only thing that has to
  run on macOS and Android.
- UI tests: minimal, on the critical onboarding path. The rest is cost without
  risk coverage.

---

## 11. Fleet tests

The last line — it catches what the lab cannot: the diversity of networks,
temperatures, firmware versions and user behaviour.

| Mechanism | Principle |
|---|---|
| Staging tenant | a full copy of the stack, a dozen or so real devices, the rest of the traffic simulated |
| Canary cohort | 1% of the fleet, min. 24 h soak before widening the wave ([CLOUD.md](CLOUD.md) 5) |
| Reference devices | a handful of units in production under constant current and log monitoring |
| Metric gate | a rise in `DISCONNECTED` or in missing `mark_boot_ok` within the cohort → automatic campaign pause |
| Game day | a timed exercise: broker failure, database failure, fleet rollback |

---

## 12. Gates

| Stage | Must pass |
|---|---|
| PR | fmt, clippy `-D warnings`, contract, unit (firmware/cloud/mobile), target matrix build, conformance on the mock, cloud integration, no size regression |
| Merge to `main` | the above + E2E on the simulator |
| Nightly | HIL on all families, fuzzing, virtual fleet soak, load tests |
| Firmware release | HIL green on the target platform + the energy test + OTA with a forced rollback on hardware |
| Rollout | canary cohort + the metric gate between waves |

The rule: **a gate is not worked around by disabling a test.** If a test is bad,
it is fixed in a separate PR with a justification — not alongside the change it
happens to be blocking.
